## What Happened

Phase C1 of template engine evolution shipped to master: `composite_anchor_json` schema v2 with quad zones + multi-zone composites. Template schema now supports both legacy rect (backward-compat) and new quad (4-point perspective) anchor kinds, with zones rendered in array order via OpenCV perspective warping.

**Stack additions:**
- Backend: `composite_anchor_json` v2 schema + read-time shim (no Alembic migration), `cv2.warpPerspective` + `INTER_LANCZOS4` interpolation, zone-aware composite orchestrator
- API: `POST /listings/from-template` body extends with optional `zone_designs: {zone_name: design_id}` map (multi-design support)
- Cache: multi-zone cache key `composites/{tid}-{sha1_10}-{Color}-multi.png` (single-design keeps legacy suffix for R2 hit)
- Tests: 218 → 237 passing (+8 anchor, +8 quad, +4 e2e)
- Deps: `opencv-python-headless==4.13` (80MB smaller than full opencv; no Qt)

## The Brutal Truth

Composite service prefetched all zone designs before checking R2 cache. Test mocked `urlopen` only on cache miss path, so multi-zone test forced a download that hit the unmocked urllib. Caught during Phase 3 (tests), ~90 min before shipping. Frustrating because it mirrored the exact failure mode from v0.4.0, suggesting we still don't have a rock-solid test isolation pattern for cache-miss scenarios.

## Technical Details

**Schema v2 design:**
```jsonc
// v1 (legacy):  {"x":0.2, "y":0.25, "w":0.6, "h":0.5}
// v2 (new):     {version: 2, zones: [{name, kind, points/rect}]}
```
- `kind="rect"`: existing Pillow `_layer_rect` path (byte-identical output)
- `kind="quad"`: 4 normalized [x,y] points → `cv2.getPerspectiveTransform` → `cv2.warpPerspective` (LANCZOS4)
- Zones composited in array order; enables front+back, logo+main, sleeve+body layouts

**Read-time migration (no DB write):**
- Old templates stored as v1 JSON stay on disk untouched
- `composite_service._envelope_anchor()` parses v1 → v2 in memory
- Zero downtime, zero data risk; migration deferred to v0.7.x cleanup

**Multi-zone cache namespace:**
- Single design: legacy filename `composites/template123-abc123-White.png` (existing R2 hits reused)
- Multi-zone: `composites/template123-abc123-White-multi.png` (new suffix avoids collision)

**Key perf trade-off:**
- `cv2.warpPerspective` on 1024×1024 base + design: ~200ms (single quad)
- Multi-zone (2 quads): ~400ms
- Acceptable; composite caching + lazy R2 retrieval hides latency

## What We Tried

1. **Pre-fetch all designs before cache check** → Broke tests, broke perf. Final: check R2 cache first, then download only missing zones.
2. **Single cache key per template regardless of zones** → Would require invalidating all zones on any change. Final: per-zone keying with `-multi.png` namespace.
3. **Full `opencv-python` dep** → Added 80MB to Docker image. Final: `headless` variant (no Qt, saves packaging overhead).
4. **Alembic migration for v1→v2** → Over-engineered. Final: read-time shim (no migration, backward-compatible).

## Root Cause Analysis

Friction came from incomplete fixture setup: test mocked R2 storage layer but didn't account for composite service's internal download path. This is a **seam violation**—when mocks sit between service layers, test must understand the full call chain, not just the entry point.

Why it repeated from v0.4.0: Phase 4 (composite logic) and Phase 5 (listing creator) were separate implementation cycles. Phase 5 test added mocks without consulting Phase 4's fixture design. No cross-phase review gate.

## Lessons Learned

1. **Cache-miss paths need explicit fixture coverage.** If a service checks cache then conditionally fetches, test must explicitly exercise both paths separately (hit + miss). Don't let mocks hide the miss path.

2. **Read-time shim > Alembic migration for backward compat.** v1 templates work immediately; no ETL risk. Deferring schema cleanup (write-side migration) to v0.7.x is YAGNI—we don't need v2-only features yet.

3. **Zone-aware caching is the right trade-off.** Multi-zone cache key complexity (per-zone tracking) is acceptable because it keeps single-design R2 hits intact and avoids overfetching.

4. **No need for 4-point UI editor in v0.5.x.** Sellers can live-edit template JSON directly (existing admin endpoints support it). Visual 4-point canvas tool deferred to v0.6.x+ unless it's a blocker.

5. **cv2.warpPerspective + LANCZOS4 good enough for mockups.** ~200ms per quad is acceptable; LANCZOS4 preserves design sharpness. Only consider psd-tools PSD smart-object path (C3) if sellers report quality gaps.
