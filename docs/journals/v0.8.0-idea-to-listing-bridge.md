## Technical Details

**4-layer schema decision:**
- `keywords` and `ideas` are user-visible CRUD targets.
- `idea_signals` is **append-only timeseries** — never updated. Velocity = `(favorers_now − favorers_first) / days_observed`, computed from the signal table on demand.
- `idea_to_listing` is composite-PK `(idea_id, listing_id)` — pure provenance, no extra fields. One idea can spawn multiple listings (re-design); one listing comes from at most one idea (idempotent on insert).

**Why a separate `EtsyPublicClient`:**
The existing `etsy_api_client` does OAuth-protected shop endpoints (PATCH listing, upload image, taxonomy). The public listings search uses a different auth pattern (`x-api-key` only, no OAuth) and a different rate envelope. Mixing them would mean two auth modes in one client. Keeping them separate also lets the miner run with zero OAuth state — useful for fresh installs that haven't connected a shop yet.

**Wizard statelessness:**
No server session. Each step's POST carries forward all prior choices as hidden form fields; the next render recomputes prefill from `idea_id` (URL) + form data. Refresh in the middle is safe. Nothing commits until step-3 submit.

**Reused listing_creator_service end-to-end:**
The wizard's submit endpoint does NOT duplicate Etsy push logic. It calls `listing_creator_service.create_from_template(...)` — the same function `/listings/from-template` uses. After success it does two extra writes: `idea_service.link_to_listing` (creates `idea_to_listing` row) and `idea_service.mark_drafted` (flips status). Both are best-effort — listing creation is the critical path; if linking fails, log + continue (the listing is still good).

**IP-warning banner:**
Step 1 renders a red banner whenever `idea.source == "extension_passive"` OR `idea.reference_image_url` is non-null. The banner copy: "Reference image is for inspiration only — redraw via Imagen before publish. Direct use is copyright risk." It's a soft barrier (you can still proceed) but it's loud.

**Notion deprecation pattern:**
Did NOT delete the Notion code. Added `NOTION_SYNC_ENABLED` flag (default false) to `Settings`. In `scheduler.py`, the two Notion jobs (`sync_to_notion`, `pull_approvals`) are conditionally registered — no jobs scheduled when flag is false. Loud startup log: `notion_sync: DISABLED (set NOTION_SYNC_ENABLED=true to re-enable)`. Code stays warm for instant reactivation.

**Miner failure model:**
Fail-closed per listing. The miner wraps each `client.get_listing(id)` in a try/except — a malformed response or HTTP 4xx/5xx logs a warning and increments `errors`, then moves to the next listing. The keyword run never crashes the scheduler. After all listings, `keyword_service.touch_last_run` updates `last_run_at` regardless of how many failed.

**E2E happy-path test:**
One test that exercises the full pipeline:
1. Seed keyword + template + design + pre-create Listing row (FK target for the mocked LCS result)
2. Run `idea_miner_service.run_for_keyword` with `EtsyPublicClient` in dry-run "happy" mode → 5 ideas + 5 signals
3. Walk Step 1 → Step 2 → Step 3 via the FastAPI TestClient — assert each returns 200 and contains the expected step indicator
4. Submit with `listing_creator_service.create_from_template` mocked to return a fixture result
5. Assert: `idea.status == "drafted"`, `idea_to_listing` row exists with composite PK `(idea_id, listing_id)`, etsy_listing_id surfaces on success page

Total runtime: 3.4s. One test, full pipeline. Easy to debug regressions.

## Root Cause Analysis

No bugs to root-cause. The only "incident" was the test count budget being way off — plan said ~12 new tests, actual was 119. That's a planning underestimate, not a problem. Each phase author wrote more comprehensive tests than the plan asked for. Worth remembering: when a phase says "~N new tests", treat that as a floor.

## Lessons Learned

1. **Plan YAML status drift is a smell.** All 7 phase files said `status: pending`, but 6 of them were 95%+ implemented in the working tree. If I'd trusted the YAML I'd have re-implemented. If I'd trusted only the YAML I'd have skipped the closeout. Always **diff plan against reality** before assuming work state.

2. **Wizard statelessness is the right call.** Zero session machinery, no server-side state to manage, refresh-safe, deep-linkable. The only cost is repetitive hidden-field plumbing in templates — minor.

3. **Reuse the working creator end-to-end.** Phase 4's biggest temptation was to "simplify" the listing creation by inlining. Resisting that and just calling `listing_creator_service.create_from_template` meant zero new Etsy push code, zero new failure modes, and the wizard inherits every fix the creator gets in v0.9+.

4. **Env-flag deprecation > delete.** Notion code stays warm. If a user complains the mobile review workflow broke after upgrade, `NOTION_SYNC_ENABLED=true` brings it back without a migration. Cheap insurance.

5. **Fail-closed per item, not per job.** The miner could have crashed the whole scheduler on one bad Etsy response. Per-listing try/except + error counter means one bad listing doesn't poison the keyword's other 24 listings, and one bad keyword doesn't poison the other 9 keywords.
