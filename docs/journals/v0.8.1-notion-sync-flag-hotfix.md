## The Brutal Truth

This is a release-discipline failure, not a coding failure. The phase-06 plan was complete down to line numbers. Some prior session ticked the success criterion `[x] NOTION_SYNC_ENABLED=false skips both jobs cleanly` without actually verifying the code path. Tests pass because no test exercised `scheduler.add_job(sync_to_notion)` being conditional — only end-to-end behavior of the jobs themselves, which still worked because the flag wasn't read.

The v0.8.0 journal even claims "In `scheduler.py`, the two Notion jobs are conditionally registered — no jobs scheduled when flag is false." Not true. The grep that took 5 seconds during regression run would have caught it before tag.

Caught it now because I ran §11 of the test-scenarios doc as a real exercise instead of trusting `pytest passed`. Two minutes of `curl /health` + `grep -n notion scheduler.py` was the difference.

## Technical Details

**Why also gate `_validate_notion_schema()` (review DB) on the same flag:**
Without gating, fresh installs with `NOTION_SYNC_ENABLED=false` still pay a startup HTTP call to Notion to validate the review DB schema — and if `NOTION_API_KEY` is empty (the common case for new Notion-deprecated users), the call returns 401 and pollutes the startup log with a warning. Gating makes "Notion is off" actually off.

**Why NOT gate `_validate_notion_idea_bank_schema()`:**
The Idea Bank is used by the extension reference-mode workflow (v0.3), which is independent of the review-sync deprecation. A user who turns off `NOTION_SYNC_ENABLED` (deprecating the review workflow) may still use the Idea Bank to save reference listings to Notion. Two distinct workflows, two distinct flags — Idea Bank stays unconditional.

**Test pattern reused:**
`test_scheduler_notion_flag.py` mirrors the structure of `test_idea_mining_scheduler.py` exactly: monkeypatch the flag, patch worker imports, intercept `scheduler.add_job` with a recorder, call `_register_jobs()`, assert on captured job IDs. DRY win — no new test infra needed.

**`/health` surface:**
Smoke now checks the flag is present (not value). Smoke total 25 → 26. The flag value reflection (true/false) is unit-tested separately.

**Runtime verify before commit:**
Two real uvicorn boots — once with `NOTION_SYNC_ENABLED=false`, once with `=true`. Confirmed:
- false: `/health` returns `"notion_sync_enabled": false`, scheduler log says SKIPPED with reactivation hint, no Notion HTTP call for review DB
- true: `/health` returns `true`, scheduler log says `Registered job: sync_to_notion (interval=30s)` + `Registered job: pull_approvals (interval=60s)`

## Root Cause Analysis

**Why was v0.8.0 tagged with phase-06 incomplete?**
The v0.8.0 ship journal says "Plan YAML status drift is a smell." It also says all 7 phase files said `pending` but 6 were implemented. Phase 6 was the one exception — the journal author treated it as implemented based on documentation, not code. The plan YAML showing `pending` was correct for phase 6; the journal "took it as done" was wrong.

**Why didn't tests catch it?**
No test asserts `sync_to_notion` is conditionally registered. The notion-sync tests assert the WORKER behaves correctly when called — which it does, because the worker is fine. The MISSING test was at the scheduler-registration level. Now exists (`test_notion_jobs_not_registered_when_disabled`).

**Why didn't smoke catch it?**
Smoke checks endpoints, not scheduler state. There was no observable surface for the flag — `/health` didn't expose it. Now does.

## Lessons Learned

1. **Documentation ≠ implementation.** A `[x]` tick in success criteria is a claim, not a verification. Before tagging, do at minimum one grep for the feature's central env var or function name. If it's not in code, it's not shipped.

2. **Flags need observable surface.** `NOTION_SYNC_ENABLED` was unobservable until v0.8.1 — no `/health` field, no startup log when false, no test. A flag without observability is a flag that can silently not exist. Pattern for future flags: (a) `/health` field, (b) startup log on both states, (c) test for both states.

3. **Regression run > regression report.** I wrote a 12-block test scenarios document earlier in this session. Reading it doesn't catch bugs. Running §11 caught this in <5 minutes. Write checklists to be executed, not filed.

4. **One missing test is worse than no tests.** 393 passing tests gave false confidence. The single missing test (scheduler registration conditional) was the one that mattered. Coverage % is a lagging indicator; "is there a test for the thing the spec says is critical?" is the leading question.

5. **Cheap revert path was the right architecture.** Phase-06 plan said "deprecate via env flag, don't delete Notion code." That decision held: the v0.8.1 fix is 53 lines of `if settings.notion_sync_enabled:` wrapping — no rewrite, no migration, no behavior change for users who set `=true`. Cheap deprecation pays off again.
